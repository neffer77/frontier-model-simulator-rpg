# P5.3.2 — Finance-owned Mail decisions

## Scope and baseline

This is one typed request, `finance.funding-gate`, not completion of the manual's entire Mail/NPC phase. It builds on PR #118 / P5.3.1, merged September 6, 2026, into `main` at `4efa51081e43dadc37ceddcc19fdb4b70b505215`. Baseline Cross-device QA run `34061713350` and Pages run `34061713333` succeeded at that SHA. This branch is not merged or deployed.

From Finance → Investment committee, propose an initiative and choose **Review funding in Mail**. The resulting thread presents an amount, gate, status, revision, committee reviewer, and explicit actions. **Open Finance** preserves the exact initiative and **Back to request** restores the same thread.

| Action | Canonical effect | Mail evidence |
| --- | --- | --- |
| Approve | Existing `gateInitiative` funds exactly one tranche, with its existing cash, evidence, risk and progress effects | One approval receipt; controls close |
| Reject | Declines this request, without spending or stopping the initiative | One rejection receipt; controls close |
| Delegate | Assigns an eligible committee reviewer, without funding | Reviewer and revision change; founder retains final approval/rejection |

Delegation is assignment, not a background NPC decision or a real multi-user permission system. An unchanged rejected request stays rejected; changing the initiative/gate creates a fresh review context. Existing direct Finance Fund/Hold/Stop controls remain available. Their changes invalidate pending reviews.

## Ownership and persistence

- `investment-committee.js` owns request creation, validation, money mutation, revisions, and the audit ledger at `state.investmentCommittee.mailRequests`. Committee schema v1 migrates additively to v2 on first request; existing decisions, scenarios, gates, and delegates survive.
- Mail schema v3 retains storage key `frontier.os.mail.v1`. Its v1/v2 migration preserves messages, flags, and NPC incident links. Typed threads carry only a `{type,id}` decision reference and project canonical audit entries into stable message IDs.
- The `finance.funding.mail.request` and `mail.decision.respond` commands use the existing command/event bus. The latter resolves the actual stored thread reference; caller-supplied entity IDs cannot retarget the decision.
- Responses require the observed `expectedRevision`. Exact retries return the prior receipt; stale/conflicting actions fail without mutation. Request creation reuses the same source fingerprint. Deleted, replaced, killed, completed, or independently changed initiatives cannot be funded from a stale request.
- Approval calls the existing gate owner with native/deferred-save options. No legacy render/ensure chain runs inside the transaction: those old chains advance portfolio progress. The fingerprint includes financial and gate inputs, identity, and prior decision count, but excludes that incidental progress.
- Cash, gate mutation, and the decision audit save together. A thrown canonical save restores in-memory snapshots. Mail saves afterward; projection failure cannot refund or duplicate funding. Reopening the thread or retrying the command reconstructs missing messages from the ledger.
- This is a local-first, single-player transaction boundary, **not multi-tab coordination**. Independent tabs/devices with divergent simulation snapshots are not protected by compare-and-swap or a server. Do not claim cross-tab exactly-once execution or authenticated reviewer authority.

## Verification and release policy

The registration/domain regression failed first on the baseline with **Missing typed Finance → Mail request command**. It now checks approve/reject/delegate, exact retries, conflicting revisions, invalid reviewers/payloads, insufficient cash, changed/missing entities, additive migration, save rollback, projection recovery and deterministic replay. These tests assert rejected commands do not mutate canonical state.

- `node tests/mail-decision-domain.mjs`: dependency-free domain test and per-command replay hashes.
- `npm run test:mail-decisions-static`: ownership, schemas, assets, workflow and blocker contracts.
- `npm run test:mail-decisions`: domain test plus pinned Playwright browser journeys.
- Browser evidence: actual Finance request, reviewer selection, delegation, approval, rejection and linked-return clicks on 390×844 and 1440×1000; real request/reject clicks and layout checks at 844×390, 834×1112 and 1920×1080. Reload, disabled stale/cash states, focus, telemetry, snapshots and zero runtime errors are asserted. Failure paths still save report, DOM, screenshot, state/events and trace.
- New focused workflow: **FrontierOS Mail decisions**. Aggregate **Cross-device browser QA** also runs the new blocker and retains its report. Use current PR Actions results as the authority for browser completion; local browser dependency setup was blocked, so browser validation runs in GitHub Actions with the user's approval.
- Release policy v16 adds `frontieros-mail-decisions`; existing blockers and the 190-route / 255-capture contracts are unchanged. PWA cache v50 ships the changed existing modules, retaining browser/PWA/Scriptable asset parity. No baseline relaxation.

Run cumulative static/build and all current-head PR checks before review handoff. Do not merge or deploy automatically. Physical iPhone touch/keyboard/scroll/PWA sign-off is still manual and cannot be replaced by Chromium emulation.

The first focused CI run caught an ambiguous reviewer control label. Its retained phone screenshot also exposed legacy gameplay navigation covering the native Mail controls. The select now has an explicit accessible name, and the legacy guidance decorator removes its old chrome without recreating it inside native apps. The browser regression explicitly rejects that overlay; legacy route and screenshot coverage stays unchanged.

The full desktop journey also exposed pointer-focus events recording a null route detail over the selected thread. Desktop window records now retain their launch payload for focus/resume. The regression asserts the persisted route after decision interactions and restores that exact thread on reload. Disabled-control assertions use stable action attributes because the existing accessibility decorator appends “Unavailable now” to labels.
