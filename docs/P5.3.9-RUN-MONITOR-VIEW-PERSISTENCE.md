# P5.3.9 — Run Monitor view persistence through reload

## Goal

Keep a Run Monitor tab selected by the player across a FrontierOS session reload without losing the incident or linked Mail advice return context.

P5.3.8 preserved the route that originally opened Run Monitor, but `setView()` changed presentation state only. The session entry could therefore continue to name the original view, so reload reopened the earlier tab.

## Ownership

The existing FrontierOS session layer remains the only navigation/session owner. It now supports updating the **current** history entry's detail in place:

- the requested app must already be the current history entry;
- the detail and derived route are replaced on that entry;
- the matching recent-app detail is refreshed;
- persistence uses the existing `frontieros.session.v1` sessionStorage snapshot;
- `os.navigation.detail-updated` records the change;
- no history entry is pushed and no second navigation store is introduced.

Run Monitor serializes its current incident, selected view, optional return thread, and optional Mail folder into the same encoded route shape introduced by P5.3.8.

## Verification

The existing NPC Mail domain and browser journeys are extended rather than creating a competing test path.

On phone (390×844) and desktop (1440×1000), the browser journey:

1. opens the linked Run Monitor from Mail;
2. confirms the original Data route and history length;
3. clicks the real **Metrics** tab;
4. confirms the current session detail changes to Metrics without increasing history length;
5. reloads the page;
6. confirms Run Monitor restores Metrics with the same incident, return thread, and Mail folder;
7. clicks **Back to advice**;
8. confirms the exact thread/folder returns and the full saved simulation + mailbox snapshot is unchanged.

Domain coverage verifies all five Mail folders, legacy no-folder links, encoded return IDs, and exact serialized Run Monitor detail.

PWA cache v59 refreshes the changed runtime. Existing release policy, blocker count, 190-route contract, 255-screenshot contract, and reviewed screenshot expectations remain unchanged. Physical iPhone/PWA verification remains manual.
