This branch is `feature/frontieros-mail-followup` and does not authorize merge/deployment.

In a pending or delegated Finance funding request, **Ask follow-up** asks: “What supports this funding gate, and what are the risks?” One deterministic committee response is stored in the same thread. This is a fixed typed question, not a free-text model service. Existing free-text replies remain separate.

The response uses the assigned eligible reviewer; otherwise it uses the first current committee member. If the assigned reviewer is no longer eligible, the request must be delegated to an eligible member before asking. No silent substitution. The existing committee `scenarioEV`, `optionValue` and `committeeStance` calculations provide amount, evidence, risk, expected value and recommendation. No NPC skill/trust/workload, cash, portfolio progress, gate or funding decision changes.

## Contracts

- Existing `mail.decision.respond` command, with `action: 'follow-up'`, resolves the stored typed thread reference and calls its domain owner. It requires the observed revision.
- One explanation per funding request. Follow-up increments revision, preserving pending/delegated status and assignment. Approve/reject remain actionable at the new revision. Asking never automatically funds or closes the request, even if the recommendation says fund/stop.
- Exact retry returns the existing receipt; a second new follow-up is rejected. Stale entity/revision, missing reviewer and invalid evidence fail without mutation. Insufficient cash does not block asking.
- The canonical committee audit saves the fixed question, response, original reviewer identity/name and calculation inputs. Rendering/reload never recomputes old explanations.
- Mail projects stable question and response message IDs from that audit. Missing response-only projection can be reconstructed without duplicating the question. Canonical save failures roll back; Mail write failures preserve the authoritative receipt for recovery.
- Additive audit fields need no storage-key or schema migration: existing Mail v3 / committee v2 saves and old audit entries continue to work. Old Mail v1/v2 migrations and P5.3.1/P5.3.2 regressions remain required.
- This remains local-first single-player behavior, without multi-tab transactions or real reviewer authentication. No backend or external model is required.
